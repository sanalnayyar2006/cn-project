Abstract—This report describes the Phase 2 extensions of a private, fully local network service platform built on two macOS hosts. A client resolves app.teamX.test through team-operated dnsmasq servers, opens an HTTPS connection to an nginx edge that terminates TLS 1.3, and is load-balanced across two Express.js backends. Phase 2 added a backup DNS resolver, TTL observation, backend isolation using the macOS packet filter (PF), passive upstream failover in nginx, and a standby edge reached by a DNS-based cutover. Controlled failure experiments showed that all 6 of 6 requests succeeded while Backend A was down, and the X-Upstream header made one nginx retry visible. Round-robin distribution resumed after recovery, and 6 of 6 requests were served by the standby edge while the primary edge was stopped. A packet capture of 3,859 frames traces one request end to end: DNS (frames 2209–2210), the TCP handshake (2219–2221), TLS 1.3 (2222–2226), and the plaintext proxied request to Backend B (2243–2247). That request takes 218.7 ms from DNS query to the encrypted response. The report also states which requirements remain partially verified: automatic operating-system DNS fallback, an unauthorized-source test from a third device, and the TTL-delayed cutover of a cached client.

Index Terms—DNS, TTL, reverse proxy, load balancing, TLS 1.3, packet filter, high availability, failover, Wireshark, troubleshooting.

I. Introduction

The course project asks each team to build a small private service environment in which "the application stays simple and the network is the project." Phase 1 delivered the working path: private DNS, two REST backends, an nginx reverse proxy and load balancer, HTTPS with a locally issued certificate, HTTP caching headers, and packet-level evidence. Phase 2 extends the same infrastructure, without rebuilding it, to answer a different question: how does the system behave when parts of it fail, and can each failure be attributed to the correct layer?

The Phase 2 objectives were to (A) add a backup DNS resolver, (B) observe TTL-governed caching during a record change, (C) restrict backend ports to the edge only, (D) fail over automatically between backends, (E) migrate traffic to a standby edge using DNS, and (F) diagnose an injected fault layer by layer. Section II lists the changes from Phase 1. Section III presents the architecture, Section IV the implementation, Section V the test method and Section VI the results, including frame-level packet analysis. Sections VII–X cover troubleshooting, learning, limitations and conclusions.

Listing 1. Backup dnsmasq configuration (Mac 3).

On Mac 2 the client side uses a macOS per-domain resolver file under /etc/resolver/ (nameserver 10.7.25.77, nameserver 10.7.2.16, timeout 2, attempts 1). scutil --dns shows two resolver sets: the default one (8.8.8.8, 10.5.7.1) for all other names, and the project one, in which the primary is tried first and the backup after a 2 s timeout. Only project names are sent to the team servers, so ordinary Internet resolution does not depend on them. The .test suffix is reserved for testing and avoids the .local conflict with macOS mDNS [1], [2].

B. Edge Reverse Proxy and Passive Failover (Extension D)

The primary edge defines an upstream pool of both backends with passive health parameters [8], [13]:

upstream backend_pool {
  server 10.7.2.16:5001 max_fails=1 fail_timeout=10s;
  server 10.7.2.16:5002 max_fails=1 fail_timeout=10s;
}
listen 443 ssl;  http2 on;
add_header X-Edge     mac2-primary   always;
add_header X-Upstream $upstream_addr always;
proxy_connect_timeout       2s;
proxy_next_upstream error timeout http_502 http_503 http_504;
proxy_next_upstream_tries   2;
proxy_next_upstream_timeout 3s;
Listing 2. Upstream and failover directives (Mac 2).

One connection failure marks a server unavailable for 10 s, and the failed request is retried on the next server, so the client does not see the error. The retry is bounded: a connect attempt is abandoned after 2 s, and at most 2 servers are tried within 3 s, so an unreachable host cannot stall a request indefinitely. The X-Upstream header exposes nginx's $upstream_addr. When a retry happens, this variable lists every server tried, which makes failover visible from the client side. These are passive checks: a server is marked unavailable only after a real request fails, and nginx does not probe it independently.

C. TLS Termination

A local CA (CN=TeamX Local CA) issued the edge certificate (CN=app.teamX.test). Its subjectAltName contains app.teamX.test and api.teamX.test, and it is valid from 24 Nov 2026 to 26 Dec 2027. Modern clients match the hostname against the SAN, not the CN [12]. The CA certificate was trusted in the Mac 2 System Keychain. Other clients validated against it explicitly with --cacert/-CAfile, and the insecure -k option was not used. The private keys were never distributed.

D. HTTP Caching

GET / returns Cache-Control: max-age=60 with an Express-generated weak ETag. GET /api/status returns no-store, because a status probe must never be served from cache [6].

E. Service Isolation with PF (Extension C)

Mac 3 loads the anchor com.apple/teamx from /etc/pf.anchors/teamx using one added load anchor line in /etc/pf.conf [10]:

pass in quick on en0 inet proto tcp from 10.7.25.77
     to 10.7.2.16 port { 5001, 5002 } keep state
block in quick on en0 inet proto tcp from any
     to 10.7.2.16 port { 5001, 5002 }
block in quick on en0 inet6 proto tcp from any
     to any port { 5001, 5002 }
Listing 3. PF anchor rules (Mac 3).

Rules are evaluated in order, and quick stops evaluation at the first match. keep state lets return traffic of an allowed connection through without a separate rule. A block with the default drop policy produces a client timeout, whereas block return would produce an immediate RST, which the client sees as "connection refused."

F. Standby Edge (Extension E)

Mac 3 runs a second nginx with the same certificate. Its upstream pool points at 127.0.0.1:5001/5002, and it identifies itself with X-Edge: mac3-standby. Because it reaches the backends over loopback, it does not weaken the PF isolation on en0.

V. Test Methodology

Each experiment followed a baseline → fault → observation → recovery → re-verification pattern. The tools used were dig for DNS, nc -vz for TCP reachability, openssl s_client for TLS, and curl for HTTP, where repeated requests were read through the X-Backend, X-Edge and X-Upstream headers. Packets were captured on Mac 2 with tcpdump -i en0, because the Wireshark GUI could not open BPF devices, and analyzed with TShark 4.6.10 and Wireshark [11]. Results were saved as timestamped text logs in the evidence directory (Appendix A). Faults were introduced only by stopping a process, editing a record or loading a rule, and every change was reverted and re-verified.

VI. Results

A. Backup DNS Resolver (Extension A)

Both servers returned app.teamX.test. 60 IN A 10.7.25.77 and the same answer for api (logs EM, HL). After the primary dnsmasq was stopped, direct queries to the backup continued to return the correct record, so name service survived the loss of the primary server. The macOS system resolver resolved both names in the showcase run. However, the experiment did not conclusively show that the resolver switched automatically from the failed primary to the backup in every case. This result is therefore reported as backup-service availability, not proven client-side failover.

The two failure types differ in where the request stops. A DNS-service failure stops the request before any TCP connection exists, because the client never learns an address. An application-server failure lets resolution and the TCP/TLS connection to the edge succeed, and the failure appears one hop later as an HTTP 502.

B. TTL and Caching (Extension B)

Both authoritative answers carried a constant TTL of 60 on every query. A server answering from its own configuration always returns the full TTL. Countdown is a property of caches. This was confirmed on a forwarded record cached by the primary dnsmasq: the TTL fell 151 → 141 → 131 at 10 s intervals (02:09:56–02:10:16), exactly one second per second. After a 135 s wait that exceeded the remaining 131 s, the cache returned a freshly fetched value (TTL 104, then 98), which shows expiry and refresh.

During the edge migration (Section VI-E), the macOS caches were flushed manually so that the new record took effect immediately. A separately logged run, in which a project record is changed and a cached client keeps the old answer until its 60 s TTL expires, remains to be recorded (Table V). In production, the same mechanism is why operators lower a record's TTL well before a migration: the time to cut traffic over is bounded by the TTL that was cached before the change.

C. Service Isolation (Extension C)

With the anchor loaded, Mac 2 reached Backend A and Backend B directly (HTTP 200 each) and through the edge (HTTP/2 200). Six HTTPS requests were split 3/3 between the backends (log FW). For the negative test, the allow rule was temporarily removed so that Mac 2 became an unauthorized source. Both connection attempts then timed out, which is consistent with a silent drop. The original rules were restored and re-verified (200, 200, HTTP/2 200). No third LAN device was available, so an unauthorized source separate from the edge and an IPv6 source were not tested.

D. Backend Failure and Recovery (Extension D)

Backend A was stopped, and a direct request to port 5001 was refused. All 6 requests through the edge then returned HTTP/2 200 from Backend B. One response carried X-Upstream: 10.7.2.16:5001, 10.7.2.16:5002: nginx tried A, received a connection error and retried B within the same client request (log BF). After A was restarted (direct HTTP 200), six requests returned the sequence B, B, A, B, A, B, all 200. The first two requests going to B is consistent with A still being inside its 10 s fail_timeout window, after which round robin resumed.

Single point of failure. The primary nginx on Mac 2 remains the SPOF, and the primary DNS shares the same host. Removing it requires a second edge plus a mechanism that moves clients to it: DNS-based cutover (demonstrated next, limited by TTL), a VRRP/keepalived virtual IP (sub-second, no DNS change), or a managed multi-zone load balancer.

E. Standby Edge and DNS Cutover (Extension E)

Before any DNS change, the standby edge was tested with curl --resolve. This override pins the hostname to 10.7.2.16 without touching DNS, and the standby returned HTTP/1.1 200 with X-Edge: mac3-standby and X-Upstream: 127.0.0.1:5001 (log EM). The app record was then changed to 10.7.2.16 on both resolvers, and client caches were flushed. With the primary nginx stopped (no listener on Mac 2:443), 6 of 6 requests succeeded through the standby (3 A, 3 B). Restoration reversed each step in order: restart nginx, check the listener and run nginx -t, restore both records, then send requests. The restored primary returned six HTTP/2 200 responses alternating A, B, A, B, A, B with X-Edge: mac2-primary. The cutover was manual. Because caches were flushed, the period in which a cached client still reaches the old edge was not separately recorded.

Three observations follow from the trace. First, ordering: resolution (2209–2210) completes before the first SYN (2219), so DNS and the connection are separate steps. Second, reliability: the server's acknowledgement number advances by exactly the number of payload bytes received (+324 after the ClientHello), which is TCP's cumulative byte-stream acknowledgement [3]. Third, termination: in TLS 1.3 only the ClientHello and ServerHello are readable. The server certificate is sent encrypted [4], so in this trace certificate validation is shown by openssl s_client (verify return code 0) rather than by a cleartext Certificate frame. The edge then issues a new, plaintext HTTP/1.1 request to the backend, which confirms the boundary drawn in Fig. 1.

G. HTTP Caching

Both backends returned Cache-Control: max-age=60 with an ETag on / and no-store on /api/status. The same header passed through the edge (HTTP/2 200). A conditional request carrying the matching If-None-Match returned 304 Not Modified with no body (log CA) [6]. A fresh hit is served from the local cache with no request at all. A conditional request costs a round trip but no body. A full request transfers the whole representation. Under round robin, A and B produce different bodies and therefore different ETags, so a validator issued by one backend matches only when the conditional request reaches that same backend.

VII. Troubleshooting Findings

The team used a fixed ladder that follows the request path: (1) dig against each resolver, (2) ping the resolved address, (3) nc -vz to the service port, (4) openssl s_client -servername with the CA, (5) curl -v while reading the edge headers, and (6) the nginx error log and pfctl -sr. The first failing rung identifies the layer. Two distinctions proved useful. A TCP refusal (port 444) means the host is up but nothing is listening, whereas a timeout (the PF test) means packets are being dropped. An HTTP 502 means DNS, TCP and TLS to the edge all succeeded and the fault lies behind the edge.

During one restoration sequence a transient HTTP 502 occurred. The nginx log reported a route-related upstream connection error. Direct backend checks passed shortly afterwards, and later requests succeeded without a configuration change. The cause was not established; a temporary Wi-Fi reachability loss between the hosts is plausible but unproven. The incident showed that a single 502 identifies the affected boundary, edge to upstream, but not its root cause.

VIII. Learning Summary

Extension A. Redundant name service is only as good as the client's willingness to use it. Configuring a second server and showing that it answers are separate claims from showing that the operating system's resolver switches to it, and the evidence for each has to be collected separately.

Extension B. TTL is decided by the authoritative server but enforced by caches. The constant 60 at the source and the falling 151 → 131 in a cache are the same mechanism seen from two sides. This explains why a DNS migration is planned around the TTL that was in place before the change.

Extension C. A stateful filter with ordered quick rules enforces "only the edge may reach the backends" without any change to the application. The choice between drop and return decides whether a blocked client sees a timeout or a refusal, and that difference is itself a diagnostic signal.

Extension D. Passive health checking hides a dead backend from clients at the cost of one failed attempt per fail_timeout window. The X-Upstream retry list and the B, B, A recovery pattern made this internal behaviour visible from the outside.

Extension E. A standby edge removes the SPOF only if clients can be moved to it. DNS can move them, but only as fast as their caches allow. The --resolve pre-check showed that the standby can be validated before production traffic depends on it.

Extension F. Working bottom-up along the request path, from name to address to port to TLS to HTTP, turns "it doesn't work" into a specific layer. Rehearsing it against the failure cases of Section VII prepared the team for the injected fault.

IX. Limitations and Future Work

  1. Automatic OS-level DNS fallback was not conclusively isolated. Future work: a capture during a primary outage showing the query moving to 10.7.2.16.
  2. Ext. B/E TTL-delayed cutover for a cached client is not yet logged. Future work: poll with curl during a record change without flushing.
  3. Isolation was verified using the edge itself as the unauthorized source. Future work: a third device and an IPv6 source.
  4. Edge failover is manual and the backend checks are passive. Future work: active probes and a keepalived virtual IP.
  5. The standby edge serves HTTP/1.1 only. Future work: enable http2 on for parity with the primary.
  6. Primary DNS and the primary edge share one host. Future work: separate hosts, or move the primary DNS to Mac 3.

X. Conclusion

Phase 2 turned a working private service into one whose behaviour under failure is measured. Backend loss caused no client-visible errors, and the nginx retry could be traced through response headers. A standby edge carried all traffic while the primary was down. A PF anchor restricted the backends to the edge, and backup DNS kept names resolvable when the primary resolver stopped. A single frame-numbered trace showed how DNS, TCP, TLS 1.3 and the plaintext proxied HTTP request fit together, including the point where encryption ends. The remaining gaps are documented with the specific experiment that would close each one: automatic resolver fallback, cached-client TTL delay, and third-device isolation.
